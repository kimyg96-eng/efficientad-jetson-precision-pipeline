STEP20A Producer-count and three-rail pipeline-energy experiment

Purpose: measure when extra CPU preprocessing producers expose the benefit of automatic FP16 versus the default weakly typed TF32 deployment engine. This is a new pipeline experiment, not the explicit-placement control against strongly typed TF32.

First run: bash run.sh pilot
Full run only after pilot review: bash run.sh full
Pilot: Bottle and Carpet, 0/1/2/4 producers, two engines, one round =16 arms, >=10s each, 3s same-mode warm-up, 2s settling. Approximate time 5–10 minutes plus file/engine loading.
Full: four categories, 8 rounds, 8 arms per category/round =256 runs and 128 paired engine comparisons; >=60s each, 10s warm-up, 5s settling. Approximately 5.5–6 hours. Use tmux and avoid any concurrent GPU work. Use Ctrl+B then D to detach without stopping a tmux session. This package's lock prevents duplicate runs of this package, not arbitrary external GPU workloads.

Preflight checks the exact SHA-256 of 410 test images and 8 deployment engines against the previously verified STEP17B source, as well as saved score/threshold inventory. No training, build or package installation is performed. Preprocessing uses the same PIL RGB / torchvision Resize(256,256) / ToTensor path. All arms set Torch intra/inter-op and OMP/MKL/OpenBLAS thread limits to1. The GPU context and stream are owned only by the main consumer thread. No CUDA work runs in producer threads.

0 producers means serial execution. 1/2/4 means that many CPU producer threads. At most5 images are in flight, including images being preprocessed, ready/reordered images, and the consumer's current image. The fixed capacity5 accommodates up to four producer-side images plus the current consumer image. Credits are taken before PNG reading and returned after the decision. The consumer preserves corpus order even if producers finish out of order. Input corpora repeat; a new corpus pass is not assigned after the duration deadline, but already assigned full passes drain. Successful runs have no discarded images and an integer number of corpus passes. Mean energy is calculated per completed image, not attributed to individual sensor samples.

Power window: host workload start before worker startup through all ordered decisions and worker joins, including fill/drain and CPU preprocessing. PNG-to-decision latency starts at each actual file read and excludes external arrivals/camera capture. Three rails are summed without idle subtraction: VDD_GPU_SOC, VDD_CPU_CV, VIN_SYS_5V0. This is not wall-plug power or a sensor-calibration claim. Raw voltage/current samples at nominal50ms and separate nominal1s clocks/temperature/fan observations are saved. Sensor retries are logged; missing critical power/active CPU/GPU/EMC or changed bounds invalidate the run. A power interpolation gap >150ms invalidates the run.

Clock handling: requires MODE_30W. After sudo authentication, clock_bounds.py snapshots active CPU/GPU/EMC min/max bounds, verifies the current maxima (CPU1728MHz, GPU612MHz, EMC3199MHz), and raises only the minimum bounds to the existing maxima. It does not call jetson_clocks, change governors, change idle states, alter fan settings or set a power mode. On exit or Ctrl+C it restores only the saved minimum bounds and verifies those selected fields plus unchanged maxima by readback. Thus the clock policy is not identical to the earlier jetson_clocks experiment (which also changed idle-state settings). Do not pool older results as the new one-producer baseline. Any failed restoration is explicitly reported; do not start further measurements until reviewed.

Protocol limits: CPU producer threads with this PIL/torchvision implementation are not GPU decoding or an optimized multiprocess decoder. Normal OS file caching is retained. The finite repeated-corpus workload is not an external camera-arrival guarantee. Within eight full rounds, producer blocks rotate and engine order alternates so each engine/producer arm occupies each within-round position once. Categories run in fixed blocks and thermal behavior is recorded. Thread startup/join are included in the energy window. CUDA-event queries, record construction and replay checks occur after each decision timestamp but inside the overall instrumented workload/energy window; power polling runs during every arm.

Every timed output is checked against the frozen score (absolute tolerance1e-6) and validation-maximum decision, and all successful inputs have frozen image hashes. Raw per-image timestamps, GPU/H2D events, queue/reorder waiting, rail traces, sensor errors, per-run metrics, protocol and clock restore readback are retained. A new evidence directory and STEP20A_REVIEW.zip are created; earlier evidence is not overwritten. Upload the ZIP named by UPLOAD_FILE even if a pilot fails, so the failure can be diagnosed.

Preparation checks are CPU-only fixtures and syntax checks; they do not establish Jetson execution success or scientific results. Run the pilot first.
